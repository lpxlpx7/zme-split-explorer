# ZME Split Explorer

Live airspace-split display for the virtual Memphis ARTCC (VATSIM), modelled on the ZTL ASX —
now with the adjacent ARTCCs' sectors and who is working them.



```bash
npm install
npm run dev      # http://localhost:5173 — also prints a Network URL to open on your phone
npm run build    # typecheck + static site in dist/ (relative paths, host anywhere)
npm run data     # regenerate public/data by hand (add -- --refresh to re-download VATGlasses)
```

The whole project is TypeScript: the app (`src/`) and the data build (`tools/`, run with `tsx`).

## How it works

- **Live data**: polls `https://data.vatsim.net/v3/vatsim-data.json` every 15 s. `MEM_*_CTR`
  controllers are matched to a sector by frequency first, then by the number in the callsign.
  A bare `MEM_CTR` counts as Razorback (22).
- **ZME split logic** (`src/ownership.ts`, rules from ZME Enroute SOP V1.3 §3-2):
  - If only combined positions (22/63/46/44) are online, the combined 2/3/4-way area split applies at all altitudes.
  - Otherwise each stratum is resolved separately. A sector goes to its own position if that is online,
    otherwise to the 4-way, 3-way, then 2-way split owner for its area. HI then falls back to the combined
    split. LO and UH fall back to whoever owns the HI airspace above or below them.
- **Adjacent ARTCCs** (`src/neighbors.ts`): ZKC, ZID, ZTL, ZJX, ZHU and ZFW sectors along the ZME
  boundary are shown per stratum and coloured by whoever is online there.
  - ZHU and ZJX publish their sectors and priority chains on VATGlasses, so ownership follows those
    chains exactly (controllers matched by frequency, then callsign number).
  - The others only have an outline on VATGlasses: their centre controllers share the strip; with
    several online the map shows the first and marks it *approx.*
- **Map labels**: every owner's position number, name and frequency is drawn on the map at all times
  (in its own sector when it works it, otherwise in the biggest sector it has).
- **Preview** (everyone, this device only): toggle positions or pick a preset, then hand any sector to any
  of those positions (list in the sheet, or click a sector on the map on a computer). The setup is kept in
  the browser's local storage and never sent anywhere. Link straight to it with `#preview`.

## Self-hosting & planned splits (admin)

Everything runs on your own server. `server/index.ts` is a dependency-free Node server that serves the
built site and the API (`/api/plans`); plans are stored in `data/plans.json`.

```bash
npm ci
VITE_OVERRIDES_URL=/api npm run build         # bake the API path into the site
ADMIN_TOKEN='<long random string>' PORT=8787 npm run serve
```

Put nginx/Caddy with HTTPS in front (proxy everything to 127.0.0.1:8787) - the token travels in a header,
so never serve it over plain HTTP. Env: `HOST`, `PORT`, `DATA_FILE`, `STATIC_DIR`, `ALLOWED_ORIGIN`
(only needed if the site is served from a different origin than the API).

**Planned splits** let the admin say ahead of time, for a time window, which positions are expected and who
covers which sector. Open the site with `#admin` appended, enter the token once; a calendar button then
appears in the header. Times are entered in UTC or your local zone (toggle; the other zone is shown next to
it), up to 72 h per plan and 90 days ahead. While you edit, the map shows the draft.

Live logins always decide: the map only ever shows positions that are really online. While a plan runs,
its sector assignments apply to those of its positions that are online; planned positions that are not
online are ignored and not shown. Finished plans are deleted automatically. Without `VITE_OVERRIDES_URL`
the feature is absent.

## Airspace data

`public/data/*` is generated by `tools/build-data.ts` from two sources:

| Source | Used for |
| --- | --- |
| Your local CRC install (`%LOCALAPPDATA%\CRC`, video maps under `VideoMaps/ZME`) | ZME sectors and combined-split regions; the adjacent facilities' sector lines (the "stubs" along the ZME boundary in `ZME_ZMEHI_F8B8_HI`, `…F9B9_UH`, `ZME_ZMELO_F2B2_LO`) |
| [VATGlasses data](https://github.com/vatglasses-project/vatglasses-data) | Every other ARTCC's boundary; ZHU/ZJX sector names, frequencies and ownership |

The ZME video maps contain only lines, so the build polygonizes them (JSTS, the JS port of JTS) and assigns
sector ids by polygon index (verified against the SOP maps). Neighbour stubs are extended outward and cut a
1.5° band around ZME into sectors, which are then matched to a facility (and, for ZHU/ZJX, a VATGlasses sector).

**You don't normally run this yourself**: `npm run dev` and `npm run build` regenerate the data
automatically whenever the CRC video maps are newer than `public/data/meta.json` (Vite plugin in
`vite.config.ts`). On machines without CRC (e.g. GitHub Actions) the committed data is used.
Set `CRC_DIR` if CRC lives somewhere else.
